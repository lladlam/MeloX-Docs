# 如何有效反馈问题

弥乐由不同平台的独立项目组成。维护者需要先知道你用的是哪个项目、哪个版本，以及问题是怎样发生的。把这些信息一次说清楚，通常比“不能用了，求修复”更容易得到有用回应。

> **本页是提问指南，不是弥乐支持服务。** 请在对应平台的公开渠道反馈；本指南的作者和《提问的智慧》原作者都不负责弥乐的技术支持。

本页参考 [《提问的智慧》中文指南](https://github.com/ryanhanwu/How-To-Ask-Questions-The-Smart-Way/blob/main/README-zh_CN.md) 的通用建议，并按弥乐的项目结构补充平台、版本、播放设备和日志信息。这里只借鉴原则，不替代或复刻上游全文。

## 提问之前

花几分钟查找已有答案，往往比重复开一个问题更快：

1. 先看[常见问题](faq)和[故障排查](troubleshooting)。
2. 在你准备发帖的平台仓库中搜索关键词、错误提示和设备型号。
3. 确认你反馈的是哪个平台项目：[Android](platforms#android)、[Windows](platforms#windows) 或 [Linux](platforms#linux)。不要把桌面端问题发到 Android 仓库。
4. 使用该项目当前提供的正式版本或构建；若问题只在开发构建中出现，注明构建来源和版本。
5. 只做安全、可逆的对照尝试，例如换一首歌、换一个输出设备或暂时关闭某项可选功能。不要为了排查而卸载清数据、公开账号凭据或执行来历不明的命令。

如果查过文档或旧问题，把查到的内容和尝试结果写出来。没有找到答案也没关系；说明你搜过什么，能帮助别人避免重复劳动。

## 先做功课，再请别人接手

维护者不是随叫随到的客服。弥乐的各平台项目由不同的人维护，很多工作是在本职工作和生活之外完成的；提交 Issue 不等于获得了排期，更不等于有人必须替你安装、配置或逐步操作。

“我不懂，帮我弄好”“你们赶快修一下”“打不开，怎么回事”都没有给别人一个可以开始调查的问题。它们把查明环境、追问步骤、猜测目标的工作全部推给回复者。先读文档、搜索已有问题、做一两个安全对照，再把结果写出来。你不需要先成为开发者，但需要说明你已经看到什么、做过什么、希望解决什么。

不必为自己不熟悉技术而道歉，也不必用“我是小白”代替问题描述。维护者需要的是事实，不是自我评价；一句“我完全不懂，求带”并不会让现象更清楚。

## 问题不是派单，也没有“紧急通道”

不要在标题加“急”“在线等”“马上要用”，不要重复催促，也不要把同一内容私信发给多个维护者。对你很着急，不代表别人已经看见，更不会自动让问题更容易定位。若问题影响范围很大，请提供可核实的影响范围和时间线，而不是用强调语气代替证据。

也不要只发一句“什么时候修好”。项目是否接受某项改动、何时有时间处理，取决于维护者的判断和精力。你可以清楚说明需求、影响和可复现情况；是否实现、如何实现以及排期由项目维护者决定。

提问时保持简洁、准确、礼貌即可。无需奉承，也无需要求私人回复。公开 Issue 让其他用户能补充信息，也让后来遇到相同问题的人能找到讨论；敏感资料则不要公开，先询问安全的提交方式。

## 选对地方，写好标题

问题应发到**发生问题的平台项目**：

- [Android Issues](https://github.com/lladlam/MeloX-Android/issues)
- [Windows Issues](https://github.com/lladlam/MeloX-Windows/issues)
- [Linux Issues](https://github.com/lladlam/MeloX-Linux/issues)

一个 Issue 讲一个主要问题。不要把同一问题同时发到多个仓库，也不要通过私人消息要求维护者优先处理。公开讨论能让有相同问题的人找到答案；维护者若需要私下收集敏感材料，会另行说明。

如果你只是想了解如何使用某项功能，先说明你要达到的目标，再说明你卡在哪一步。“怎样点这个按钮”可能真正的问题是“我想把手机正在播放的音乐送到客厅音箱”；目标不同，合适的功能也可能不同。

先判断你要发的是哪一种内容：

- **使用问题**：功能入口或操作方式不清楚。先写你的目标、当前看到的页面和卡住的步骤。
- **缺陷报告**：已有功能没有按预期工作。提供环境、复现步骤、预期和实际结果。
- **功能建议**：当前没有你需要的能力。描述使用场景、希望解决的具体问题，以及现有方式为什么不够；不要把“我想要”写成“软件坏了”。
- **服务可用性问题**：第三方音源、登录、歌曲资源或接口失效。说明服务、时间、地区（如相关）和对照结果；第三方服务变化不一定能由弥乐修复。

这几类问题的调查方式不同。先把问题分清楚，回复者才知道你是在问怎么用、报告异常，还是建议新增能力。

标题写清楚**平台/功能 + 现象**，不要只写“求助”“急”“有 Bug”。例如：

- `Android / USB：授权 UAC1 DAC 后播放仍无声`
- `Windows / 搜索：切换到 QQ 音乐后结果页持续加载`
- `Linux / 播放：Arch KDE Wayland 下开始播放后没有声音`

对照一下：

| 不够有用 | 更容易调查 |
|---|---|
| `救命，弥乐坏了` | `Android / 下载：Wi-Fi 下下载任务停在 0%，单曲也可复现` |
| `Windows 版有 Bug` | `Windows / 搜索：切换 QQ 音乐后搜索页持续显示加载状态` |
| `为什么不支持我的 DAC？` | `Android / USB：DAC 型号 X，授权后提示不支持 UAC2` |
| `什么时候修，急用` | `Linux / 启动：某发行版上启动即退出，附版本和错误输出` |

先报告观察到的现象，不必先断定“这是某某代码的 Bug”。原因可以作为猜测提出，但请标明是猜测，并把事实和推论分开。

## 让文字容易读、信息容易核对

使用普通文字和清楚的段落。错误信息、命令输出和日志片段应原样放在代码块中；不要把文字截成模糊的照片，也不要上传需要特殊商业软件才能打开的文档。截图可以帮助展示界面，但不能代替版本号、错误文本和复现步骤。

长日志不等于好报告。先定位问题发生的时间，只摘录相关上下文；如果完整日志确实必要，说明为什么需要，并在上传前检查隐私。不要把几十张截图、整个应用目录或与问题无关的系统报告一股脑扔给维护者，让对方替你找线索。

标题和正文不要全大写、堆叹号或反复写“救命”。简短、准确、可搜索，比情绪强烈更有用。语气不需要卑微；尊重对话双方即可。

## 把问题说到可以复现

按发生顺序描述：从哪个页面或操作开始，做了什么，应用如何响应，问题在哪一步出现。写出你**期望发生什么**和**实际发生什么**，并尽量给一个最小复现过程。

例如，“播放坏了”无法判断问题在哪。可以改写为：

> Android 0.7.1，Pixel 8，Android 16。选择网易云音源，播放两首歌曲都正常；连接某型号 USB DAC，在系统授权后选择“USB 独占”，播放页进度正常增长，但 DAC 没有声音。切回手机扬声器后有声音。每次都能复现。尚未尝试其他 DAC。

这段描述给出了范围、对照结果和复现频率，没有先猜测原因。若问题只涉及某首歌曲或账号权限，可用能公开的信息说明；不愿公开歌曲记录时，描述音源、资源类型和失败现象即可。

请贴有用的部分，而不是一大段无关截图或完整日志。截图应能看出相关页面和错误文字；日志注明导出时间及问题复现时间。若问题不稳定，说明发生次数、最近一次时间，以及每次之前做过什么。

把观察和猜测分开。比如“点播放后进度变了，但没有声音”是观察；“应该是解码器坏了”是猜测。先把观察写全，猜测可以附在最后，并说明依据。不要只写结论，让别人替你反向推测过程。

如果功能没有达到你的目标，也请说出目标。是希望在电脑上控制手机、把音频发到音箱，还是让两台设备同步播放？这些可能对应不同功能。只报告“投屏不好用”，别人无法知道你期待的是哪一种行为。

## 可直接复制的模板

```text
标题：<平台 / 功能：具体现象>

项目：<Android / Windows / Linux>
弥乐版本或构建来源：
操作系统版本：
设备型号与架构：<手机型号 / Windows 版本 / Linux 发行版与 x86_64 等>
相关音源、文件或外接设备：<没有则写“不涉及”>

复现步骤：
1.
2.
3.

预期结果：
实际结果：
复现频率：<每次 / 偶尔 / 暂未复现>
已查阅或尝试：<查过的文档/旧问题，以及尝试结果>

日志或截图：<已附 / 未附；附上前已检查隐私>
```

不知道某一项就写“不清楚”，不要猜一个答案。与问题无关的字段可以删掉。

## 按问题类型补充

### 播放或音源

- 说明当前平台、音源、目标音质，以及是搜索无结果、解析失败、无法开始、播放中断还是有进度但无声。
- 说明同一音源的其他歌曲是否可播；如果方便，说明切换输出设备或音源后的对照结果。
- 使用第三方脚本时，说明脚本来源、版本或最近更新时间。不要贴含密钥的脚本配置、Cookie、Token 或私有播放链接。
- 避免把请求 URL、账号内容或可识别个人收听记录直接放进公开 Issue。

### 外接设备或局域网

- Android USB：提供手机、Android 版本、DAC 与转接头型号，说明是否出现系统 USB 授权、选择了哪种输出，以及失败在哪一步。先核对 [USB 支持范围](usb-audio)。
- Windows/Linux 音频：说明操作系统版本、桌面环境、音频设备名称和应用构建来源；Android USB 独占步骤不适用于桌面版本。
- 局域网：说明发送端、接收端、网络类型，以及问题发生在发现、配对、连接、控制还是出声阶段。不要公开配对 PIN、家庭网络密码或公网地址。
- DLNA/MiPlay：注明接收设备型号和系统/固件版本；“发现设备”与“持续播放成功”是不同结果。

### 崩溃、卡顿或安装问题

- 说明问题从哪个版本开始、是否每次发生，以及最近是否更换了应用构建、系统或音频设备。
- Linux 请注明发行版、桌面环境（X11/Wayland）和 CPU 架构；Windows 请注明 Windows 版本及安装包/构建来源。
- 如果应用启动即退出，提供错误提示和相关日志片段；尽量只摘录问题时间附近的内容，并保留原始错误文本。
- 不要为“试试看”卸载应用或清除数据。若必须执行会删除数据的步骤，先确认备份和数据影响。

### 功能建议

- 说清楚你要完成的事情，以及目前如何完成、在哪一步受阻。
- 描述对你有帮助的结果，不必替维护者规定具体实现方案。
- 如果只是个人偏好，也可以直接说明；不要把偏好说成所有用户都遇到的缺陷。
- 搜索现有 Issue，若已有相近建议，就在原讨论中补充你的场景，而不是重复开多个相同请求。

例如，与其写“加一个和某应用一模一样的按钮”，不如写“我经常在桌面上切换歌词和队列，希望能在不离开当前页面时查看队列；目前需要反复打开/关闭播放页”。前者限定实现，后者说明目标和实际阻碍。

## 怎样回应回复

收到建议后，先按步骤测试，再报告结果。可以说明“按建议关闭某设置后问题消失；重新开启后又出现”，这比“还是不行”有用得多。若建议不适用，说明具体哪一步做不到、界面显示什么；不要只回“没用”。

回复者提供的是线索，不一定是最终结论。你可以礼貌地追问不理解的术语，或指出建议与当前现象不符，并附上证据。不要把不同意见变成对人的评价，也不要假定对方必须替你远程操作、写完整教程或承诺修复。

如果找到临时绕过方法，也请明确它是 workaround，不要把它说成根因已经修复。应用更新后再验证一次；确认解决后回到原问题报告结果。

## 日志与隐私

日志可能包含账号状态、歌曲或播放信息、请求 URL、设备信息和第三方服务响应。即使应用会对部分字段脱敏，也不要假设日志完全匿名。

Android 可从“设置 → 关于”导出 MeloX 全部日志。Windows/Linux 的日志位置和导出方式依桌面项目实现而定；请先查看对应仓库 README，不要套用 Android 的菜单路径。

发布前检查附件和文本，删除密码、Cookie、Token、个人 API Key、私有播放链接、家庭服务器地址、个人联系方式及其他不愿公开的信息。若无法安全地公开日志，先在 Issue 说明，并询问项目维护者是否有合适的私下提交方式；不要把敏感材料直接贴在公开讨论中。

更多细节见[隐私与日志](privacy-and-logs)。

## 回复之后

如果维护者追问信息，请在原讨论串补充，并说明新信息改变了什么。问题解决后，留一句原因和解决办法；如果无法复现，也请说明。这能让后来遇到相同情况的人少走弯路。

若几天没有回复，不要把沉默解读成针对你，也不要连续顶帖。检查仓库是否选对、信息是否齐全；确有新证据时，在原 Issue 补充。项目可能没有足够人手处理每一个问题，未回复不代表有人承诺会解决。

如果问题仍未解决，可以编辑原 Issue，让标题、复现步骤或日志说明更准确；不要删掉原讨论后在多个地方重新发一遍。若确认是第三方服务暂时不可用，写明恢复时间或服务状态；若问题只在旧版本存在，也注明升级后是否消失。

感谢愿意复现问题、认真描述现象并跟进结果的每一位用户。开源维护通常没有专职支持团队；清楚、准确、公开的问题报告，是对维护者和其他用户最有效的帮助。

## 也可以帮助别人

看到自己遇过的问题时，可以分享你验证过的解决步骤，并说明适用的平台和版本。不要只回复“我这里正常”，也不要把自己的单次结果当成普遍结论。好的补充会让讨论更完整；不确定时，提出澄清问题比猜测原因更有帮助。
